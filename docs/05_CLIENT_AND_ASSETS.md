# 客户端与资源设计

## 屏幕与交互

初版横屏，1280×720 只作设计坐标参考，布局按有效安全区伸缩。底部本人手牌与动作区优先；对家背牌可简化为牌数，保留四席方位。信息拥挤时收起历史牌河，不缩小核心点击目标。

主动作及可点击字牌建议至少 44×44 逻辑像素；这是设计目标，不是微信平台法定值。关键文字在目标手机可读。刘海、圆角、胶囊与软键盘都不遮提交/投票。

选字序列与选图序列分开；点击选择、再次点击取消。拖动必须有明确按住阈值和位移阈值，纵向滚动与横向重排互斥；保留点选后左右移动的可访问替代。无 hover 的手机上用长按预览/详情，不能依赖 tooltip 才能发现关键词。

投票页面保留“两步”：认可/反对 → 有图时评分 → 原子提交；无图第一步直接提交 rating=0。等待其他人时展示人数，不展示私有选择或临时平均分。

## UI 状态

客户端 Controller 保存 view、draft、connection、pendingCommands。提交后显示待确认；不能提前移牌或加分。ACK 丢失不生成新 command_id 重试。收到新快照时保留仍合法的草稿，round/turn/proposal 改变则清理过时草稿。

事件动画按 event_id 去重；快照先落地，再播放可选动画。重连允许跳过动画，不依靠播放完成回调推进逻辑。

PlatformPort 负责 login、shareRoom、onForeground、onBackground、storage、getSafeArea。资源与核心规则不直接读取 wx。

## 资源现状与目标

源项目盘点（2026-09-27）：82 个目录资产，74 个表情，59 个动画；assets 46.25 MiB，content 178.73 MiB，其中 sheets 175.59 MiB、previews 2.98 MiB。是源目录统计，不是微信发布包大小。

最大帧图 2400×4763，RGBA 展开约 43.6 MiB/张。现 Godot 拆帧/压缩/缓存方式不直接移植。

初版选择约 12–20 张表情（少量代表性动图可晚于静态闭环加入）。NBA/LOL 字库保留 JSON；所有表情逐步迁入，不能为了抢首版一次预加载整个库。

## 素材清单模型

```json
{
  "schema_version": 1,
  "content_version": "content-001",
  "rules_version": "word-tiles-4",
  "memes": [{
    "key": "stable-existing-key",
    "title": "显示名称",
    "keywords": ["开心"],
    "preview": {"path": "thumbs/key.png", "sha256": "build-generated", "bytes": 12000},
    "animation": null,
    "license_note": "从原目录保留待核验信息"
  }]
}
```

示例 hash 为占位，生成器必须产出真实值。外部路径由可信清单定义，玩家不能指定下载 URL。

资源版本在房间创建时冻结。更新目录不能让同一 key 在同一局变成另一张图；新资源以新 content_version 发布。资源加载失败仍展示占位和原有 key/标题，投票行为保持确定。

## 动画方案

先评估缩小后的分帧图集：按显示尺寸限制单帧，限制帧率/时长，预先生成图集与帧元数据；运行时播放图集帧，不再现场裁切压缩全部 PNG。图集最大边长与压缩格式按目标设备能力验证，不能假定 S3TC 或动画 WebP 跨设备都可用。

仅当前可见/播放的动画占用活跃资源，列表使用静态预览。旧请求完成后核对当前 key/页面代次，防止快速切图导致错图。缓存按估算解码纹理字节设置上限，并以真机实测校正。

## 初始质量预算（验收目标，不是已测结果）

- 代表设备上冷启动到可操作菜单：普通网络目标 5 秒内。
- 已加载资源时点牌/选项反馈：目标 100ms 内。
- 首场景资源预算先按 3 MiB 内规划，最终平台限制与引擎包另核验。
- 首版必要远程素材集目标 10 MiB 内；不得自动全库下载。
- 动画缓存初始预算 32–64 MiB，由测试决定；统计纹理而非 PNG 文件大小。
- 持续十局/30 分钟后，释放回菜单的内存不持续单调增长。

字体先用跨平台可靠系统回退验证全部牌面；需要统一牌面字体时采用授权字体并子集化，不打包整套大中文字体。测试两套字库所有字及常用 UI 文案。
